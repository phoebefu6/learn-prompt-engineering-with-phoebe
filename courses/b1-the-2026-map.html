Part 1 · the method

Success criteria before prompts 5 min live

Anthropic's prompt engineering docs open with a funnel, not a technique: define success criteria, build empirical evals, draft a prompt - and only then start engineering it. Their official Skilljar API course makes the same move: the evals module comes before the techniques module. That ordering is deliberate, and it is the single biggest habit difference between hobbyists and practitioners.

LiveWhy criteria come first - the practitioner's reason3 min▶

Without written criteria, "better prompt" means "the output I happened to like this afternoon". You will tweak forever because there is no finish line. With criteria, prompt engineering becomes normal engineering:

  • You know when to stop. "Category accuracy at 90% on the test set" is done or not done.
  • You can compare fairly. Two prompt versions, same 10 tickets, count the wins. No memory bias.
  • You can change models safely. When a new model ships, rerun the set. Criteria outlive any one model.
The 10-case rule You do not need an eval framework today. Ten realistic inputs with expected answers, in a spreadsheet, is a legitimate eval. Anthropic's own eval docs say volume of test cases matters more than grading sophistication. We start exactly that small in the build-along.
Self-studyWhere fine-tuning fits - the decision boundary2 min read▶

One boundary mention, once, so it never distracts again: prompting is almost always the first tool, because it is instant, cheap, and reversible. Fine-tuning enters only when you have strong evals proving that prompting has plateaued, plus thousands of examples and a stable task. If you cannot measure the gap, you are not ready to fine-tune - which is another reason the funnel starts with criteria. This track does not cover fine-tuning further; the funnel is the point.

Part 2 · the terrain

Prompting inside context engineering 5 min live

Anthropic's 2025 framing renamed the wider game: context engineering is curating everything that lands in the model's context window - system prompt, retrieved documents, tool outputs, conversation history - aiming for the smallest set of high-signal tokens that gets the job done. The prompt did not get less important. It got a precise job title: it is the one layer of the context you fully control.

LiveWhy the industry renamed the game3 min▶

Three practical consequences of the context-engineering frame, before we zoom back into the prompt layer for the next few sessions:

  • Signal over volume. Stuffing the window hurts. Every irrelevant token competes with the relevant ones. Curation - choosing what NOT to include - is real work.
  • The prompt is the constant. Retrieval varies per query, history grows per turn, tools return whatever they return. Your prompt is the stable contract holding it together - which is why it deserves engineering discipline.
  • Techniques still work. What died was the standalone "prompt engineer" job title, not the skill. The skill got absorbed into every builder role, the way SQL did.
Self-studyThree words you will hear later: compaction, just-in-time retrieval, subagents2 min read▶

Anthropic's context-engineering post names three techniques for keeping windows lean. Today, names only - each gets real treatment later in the track:

  • Compaction: summarizing older history into a short note so long conversations do not drown the window. Session 5.
  • Just-in-time retrieval: fetching documents at the moment they are needed instead of preloading everything. Session 5.
  • Subagents: handing a subtask its own fresh context window and getting back only the conclusion. Session 6.
Part 3 · the fork in the road

Which model class am I prompting? 6 min live

This is the question that decides which advice applies. Reasoning models plan internally before answering; classic prompting tricks that induce planning can now actively hurt them. Standard models still respond to those tricks exactly as the 2023 playbook says. Ask this question first, every time, or you will apply the right technique to the wrong model.

Live2023 advice vs 2026 advice, side by side3 min▶
2023 said2026 says (reasoning models)
Always add "think step by step"Never add it - the model plans internally; the phrase can degrade output
More examples = betterZero-shot first; OpenAI measured reasoning models doing worse WITH examples
Spell out the method in detailState the goal, constraints, and success bar; let it choose the method
Tune temperature and top_pUse effort / reasoning parameters; some current models reject sampling params outright
Long elaborate role-play personasShort domain framing; heavy personas demoted by Anthropic's own guidance
Real world

The classic failure: a team upgrades to a reasoning model, keeps their lovingly tuned 2023 mega-prompt full of "think carefully, step 1, step 2" scaffolding - and quality drops. They blame the model. The prompt was fighting the model's own planning. Deleting half the prompt fixed it.

Build-along

Meet TriageBot: criteria first, then v0 ★ 22 min · laptops open

Meridian Retail's support inbox gets hundreds of tickets a day. Our job across this track: a prompt system that classifies each ticket, summarizes it, and routes it - reliably enough to trust. Today we practice the funnel from Part 1 on it: criteria before prompt.

LiveThe raw material: 10 Meridian tickets3 min▶

Your working test set - real inbox energy, typos and rage included. Keep these; they follow us to session 10.

  1. "Charged twice for order #48210, refund one please"
  2. "Where is my parcel?? Ordered 9 days ago, tracking frozen since Tuesday"
  3. "The kettle arrived dented, I want to send it back"
  4. "Your website charged my card but shows no order confirmation???"
  5. "Jacket is lovely but too small - how do I exchange for a size up?"
  6. "Driver left the box in the rain, everything inside is soaked"
  7. "I keep getting someone else's invoices by email, this is the third time"
  8. "Cancel my order if it has not shipped, otherwise ignore this"
  9. "hi"
  10. "Store staff were great but the app deleted my loyalty points AND my last order shows twice on my statement"

Notice tickets 8, 9, and 10: conditional, empty, and genuinely two-category. Every real inbox has them. They exist to punish naive prompts.

TriageBot v0 - the naive draft everyone writes firstCategorize this support ticket: [paste ticket here]
TriageBot v0.1 - the same ask with criteria baked inYou are TriageBot, the support-ticket triage assistant for Meridian Retail. Read the ticket below and output exactly this: Category: one of BILLING, SHIPPING, RETURNS, UNSURE Summary: one sentence, max 25 words, neutral tone Rules: - Use only facts stated in the ticket. Never invent order numbers, names, or amounts. - If the ticket fits no category, fits two equally, or lacks enough information, output UNSURE. Ticket: [paste one ticket here]

Read the 10 raw tickets. Before writing anything, decide what categories even exist. We settle on BILLING, SHIPPING, RETURNS, and UNSURE for everything else - small on purpose.

Write success criteria FIRST. Ours: category accuracy 9/10 or better on the test set · summary 25 words or fewer · neutral tone even when the customer is furious · zero invented order numbers or amounts. Write yours down before touching the prompt.

Draft v0, the naive one. Run the bad box above on tickets 2, 9, and 10. Watch it invent categories you never defined, guess on "hi", and pick one category for ticket 10 without telling you it dropped the other.

Write v0.1 with criteria baked in. Role, enumerated categories, output format, and the UNSURE escape hatch. Run the same three tickets and compare against your written criteria - not against your mood.

Save both versions and the criteria. A file, a gist, anywhere durable. In session 8 those criteria become a real eval, and v0 becomes your baseline to beat on a scoreboard.

The habit this plants Nothing about v0.1 is clever - no technique from later sessions appears in it. It is better purely because the success criteria existed before the prompt did. That ordering, not any phrasing trick, is today's takeaway.
Homework

Three things before session 2 ◐ 25 min total

  • Label the full test set. Assign your own expected category to all 10 tickets and note the two you found hardest to label - if a human hesitates, the criteria need a rule for it.
  • Run v0.1 on all 10 tickets in your chat UI or API of choice. Score it against your criteria: how many categories correct? Any invented details? Bring the number.
  • Classify your models. List the 2-3 models you use most at work and decide which side of the Part 3 decision tree each sits on. If you are not sure, check the vendor's docs for a thinking or reasoning mode - that is your answer.

Check yourself

Three questions before you go 🎯 ◐ 90 seconds

1 · Anthropic's official working order for prompt development is...

The funnel runs criteria → evals → draft → engineer. Their Skilljar course even teaches evals before techniques - the ordering is the method, not an accident.

2 · You are prompting a reasoning model. Which habit should you drop?

Reasoning models plan internally: induced CoT is redundant-to-harmful, and few-shot examples can measurably hurt. Go zero-shot first and steer depth with effort or reasoning parameters.

3 · Context engineering is best described as...

It is the wider discipline of managing the whole token ecosystem. The prompt remains the one layer you fully control - which is exactly why this course exists inside that bigger frame.
